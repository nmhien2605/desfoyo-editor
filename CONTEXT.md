# Desfoyo Editor

A React component library for a graphic-design canvas editor (Canva-like) with a PixiJS/WebGL text-effects engine (Kittl-like) as its core differentiator.

## Language

**Node**:
A serializable element in the document's scene graph (`text`, `shape`, `image`, `svg`, `group`), discriminated by `type`. The valid set of node types is phase-scoped — Phase 1 accepted only `text | shape | image`; `group` arrived in Phase 2 (see **GroupNode** below); `svg` is still reserved for Phase 4. A document containing an out-of-phase node type is invalid, not silently ignored. Nodes can now nest arbitrarily deep (a `GroupNode`'s `children` can contain other groups) — lookups always go through `src/core/tree.ts`'s recursive walk (`findNodeInTree`/`requireNodeInPage`), never a flat `.find()`, so nesting depth is transparent to every call site.

**GroupNode**:
A real `Node` (`type: 'group'`) whose `children: Node[]` render inside its own transform. Distinct from **multi-select** (see below) — grouping is an explicit, undoable structural command (`GroupNodes`/`UngroupNode`) that moves nodes between containers and rewrites their transforms to the new parent's local space; multi-select is a transient UI aggregation that never touches document structure. Dragging/rotating/resizing a `GroupNode` needs no special math (Pixi's container nesting handles it automatically); only *ungrouped* multi-select transform needs the dedicated math in `groupTransformMath.ts`.
_Avoid_: "Group" alone when the distinction matters — say "GroupNode" for the structural node, "multi-select" for the transient UI selection of several nodes.

**Selection**:
The set of currently-selected `nodeId`s (`uiSlice.selectedNodeIds: Set<string>`), never part of the document — ephemeral UI state, not undoable, not persisted. Plain click replaces the selection; shift-click toggles a node in/out. Distinct from **GroupNode**: selecting multiple nodes and transforming them together does not create document structure.
_Avoid_: "selectedNodeId" (singular) — Phase 1's single-select field was replaced Phase 2; every call site is selection-*count*-aware (1 vs many branch differently in `SelectionOverlay`).

**Command**:
A named, typed request to mutate the document (e.g. `AddNode`, `RemoveNode`, `UpdateProps`, `UpdateTransform`, `Reorder`, `GroupNodes`, `UngroupNode`). Every document mutation goes through a Command — there is no direct model mutation path. A Command carries the `nodeId`(s) it affects (and, since Phase 2, an optional `parentId` on `AddNode`/`RemoveNode`/`Reorder` naming which `GroupNode` — or the page directly — owns the affected array), which the SceneReconciler uses for targeted invalidation instead of diffing the whole tree.
_Avoid_: Action, mutation, event (Command is the specific term for this project's mutation-request objects)

**History / Gesture**:
Undo/redo is patch-based (Immer `produceWithPatches`), not command apply/invert — reuses the store's existing Immer usage instead of hand-writing an inverse for every Command. A **Gesture** (`beginGesture(id)`/`endGesture()`) is the coalescing unit: a continuous interaction (drag, resize, rotate, multi-delete, paste) dispatches many times but commits exactly one history entry, computed once at gesture end as the single patch set from the gesture's start-document to its end-document. Setting `lastCommand: null` (done by undo/redo and by `loadDocument()`) is the specific signal that tells `CanvasHost` to do a full scene rebuild instead of a targeted `reconciler.apply()`.
_Avoid_: "Transaction" (this project's term is Gesture, scoped specifically to continuous pointer/slider interactions, not general grouping of commands)

**Camera**:
Ephemeral zoom/pan viewport state (`uiSlice.camera: { zoom, panX, panY }`) — never part of the document, never goes through `dispatch`/history. Applied directly to `pageContainer.scale`/`.position` in `CanvasHost`. `viewport.ts`'s `toWorld`/`toScreen` convert between native-event (viewport-relative) coordinates, world (document) coordinates, and the canvas-local pixel space that `SelectionOverlay`'s DOM handles are positioned in — these three spaces coincided in Phase 1 (no camera) and now genuinely differ.

**Page switching** (Phase 4 Pass A):
`uiSlice.activePageId` + `setActivePage()` existed since Phase 1/2, but until this pass changing it had **no effect on the Pixi scene** — `CanvasHost.tsx`'s mount effect only reacted to `document`/`lastCommand` changes, neither of which a bare page switch touches, so the canvas silently kept showing the *previous* page's content while every other panel (`LayersPanel`, `SelectionOverlay`, `PropertiesPanel`, `Rulers`, all of which read `activePageId` reactively) instantly reflected the new page. This was a real bug sitting dormant since Phase 1, only exposed once Pass A added a way to actually switch pages. Fixed by a third `store.subscribe` branch in `CanvasHost.tsx` that fires on `activePageId` changes and calls a shared `remountPage(page, doc)` closure — also factored out of the pre-existing "wholesale document replacement" branch, which had the same latent gap (a `loadDocument()` to a differently-sized page never resized the renderer either). `remountPage` resizes `app.renderer` to the new page's `size`, reapplies `app.renderer.background.color`, redraws the grid, and remounts the `SceneReconciler` against the new page — every page-level Command (`AddPage`/`RemovePage`/`ReorderPage`/`DuplicatePage`) intentionally has no `SceneReconciler.apply()` case, since `remountPage` firing on the resulting `activePageId` change is the only visual consequence any of them can have (see `isPageLevelCommand` in `src/core/commands.ts`).

**Snapping / Guides / Grid**:
Phase 2 additions, all ephemeral (never touch the document or history) and camera-aware. Smart-guide snapping (`src/render/interactions/snapping.ts`'s `computeSnap`) matches a dragged selection's edges/center against sibling nodes' and the page's edges/center, within a threshold that's divided by `camera.zoom` so it feels consistent at any zoom level; matches are surfaced as `uiSlice.activeGuides` for the overlay to draw. Snap-to-grid (`uiSlice.grid`) is independent and only kicks in on an axis the object-snap didn't already claim. Marquee (rubber-band) selection (`src/render/interactions/marquee.ts`) is the third ephemeral interaction in this family — `uiSlice.marqueeRect`, cleared on pointerup.

**Effect**:
A named visual post-process (`shadow`, `inner-shadow`, `glow`, `outline`, `extrude3d`, `blur`, `custom`) attached to a node's `effects: Effect[]` and fully declared in `src/schema/effect.ts` — but a schema-valid effect only actually renders if `src/effects/buildFilters.ts` has a matching case building a real `pixi-filters`/`pixi.js` `Filter`; otherwise it's silently inert (no crash, just no visual). As of Phase 3 Pass D, every variant renders: `shadow`/`glow`/`outline`/`blur` map 1:1 to existing `pixi-filters`/`pixi.js` filters, `extrude3d` is `BevelFilter` for non-text nodes (real stacked-clone geometry for text — see **Real 3D extrude**), `inner-shadow` is a hand-written GLSL `Filter` (`src/effects/shaders/innerShadow.frag.ts`, a single-pass 5-tap approximate blur, not a true Gaussian), and `custom` looks up `effect.shaderId` in `src/effects/shaders/customShaders.ts`'s `Record<string, string>` registry — **not arbitrary user-authored GLSL**, just a small built-in named-shader library (currently just `chromatic-aberration`); an unknown `shaderId` stays silently inert, same convention as before any of this existed.
_Avoid_: assuming `custom` means users can paste their own shader source — it's a fixed registry lookup by design, to avoid the compile-error-UX/sandboxing surface arbitrary GLSL would need.

**Stroke layers**:
`Stroke.layers: { width, fill, offset? }[]` (on both `ShapeNode.stroke` and `TextNode.stroke`) makes a stroke N concentric/offset outline passes instead of one — the layered-outline look Kittl-style presets use. No dedicated Command; it's just part of the `Stroke` value edited via `UpdateProps`. Rendered by redrawing the shape's path (or, for text, stacking stroke-only `Text` clones) once per layer at its own offset, all painted behind the true fill on top.

**Warp**:
`TextNode.warp: { type, intensity, pathId? }` deforms a text node's rendering (`arc`/`wave`/`bulge`/`flag`/`perspective` as of Phase 3 Pass A; `path` added in Pass C, see **Path** below). Deliberately implemented **without opentype.js or any glyph-outline parsing** — `textRenderer.ts` rasterizes the node's normal flat rendering to a `Texture` via `renderer.generateTexture()`, then maps that texture onto a deformed `PIXI.Mesh` whose vertex grid comes from pure functions in `src/text/warpGeometry.ts`. This is whole-texture deformation, not per-glyph vector deformation — coarser, but matches the phase doc's own "flat text stays `PIXI.Text`, warped text becomes mesh geometry" strategy without a font-parsing dependency. Plain (unwarped) text stays a bare `PIXI.Text` — no behavior or perf cost for the common case. The live `PIXI.Renderer` (needed for `generateTexture()`) is threaded via a module-level singleton, `src/render/rendererContext.ts` (`setRenderer`/`getRenderer`), set once by `CanvasHost.tsx` rather than as a parameter through every renderer — justified because there's exactly one `PIXI.Application`/renderer per mount for its whole lifetime. `getRenderer()` returns `undefined` in tests (jsdom never calls `app.init()`), and warped text falls back to flat rendering in that case — correct offline/test behavior, not a gap.
_Avoid_: assuming glyph-level outline deformation is happening anywhere — it isn't, by design.

**Path** (Phase 3 Pass C):
`document.paths: Record<pathId, PathData>` — a document-level dictionary (same shape as `assets`), each entry one open quadratic bezier (`points`: 3 normalized `(u,v)` pairs in 0..1, start/control/end). `TextNode.warp.pathId` references an entry; the properties panel auto-creates a default arc on first selecting the `'path'` warp type, edited via 3 draggable dot handles in `SelectionOverlay.tsx` (no dedicated pen tool). `warpGeometry.ts`'s `computePathGrid` arc-length-samples the curve so text doesn't bunch up on tight bends, and offsets the mesh's two rows *perpendicular to the tangent* (not just vertically, like the other warp types) so the text band doesn't shear on steep curves. A missing/stale `pathId` falls back to a synthesized straight-line path (renders flat, no throw). Mesh warp and the `extrude3d` effect are mutually exclusive in the UI (both swap the text node's render-object shape — see below) rather than building a combined renderer path for a rare combo.
_Avoid_: "path" alone when it could mean `ShapeNode.shape: 'path'` (unrelated — arbitrary SVG path data, still an unimplemented stub in `shapeRenderer.ts`) instead of this text-warp path.

**Render-object identity swap** (`needsRecreate`):
A text node's rendered Pixi object is one of four mutually exclusive shapes depending on its props: bare `Text` (plain), `Container` tagged `'stroke'` (multi-layer stroke), `Container` tagged `'extrude'` (Phase 3 Pass C's real 3D extrude — see below), or `Mesh` (active mesh warp). `SceneReconciler.ts`'s `update()` can mutate any one of these in place, but can't turn one into another — crossing that boundary (stroke/extrude/warp added to/removed from a node, or warp *type* changing to a different vertex-grid row count) needs the object destroyed and recreated at the same tree position, which `textRenderer.ts`'s exported `needsTextRecreate()` detects (single source of truth for all four shapes) before `SceneReconciler.apply()` decides between `update()` and a full recreate (same mechanism already used for `AddNode`/`RemoveNode`). Two `Container`-producing cases (`'stroke'`/`'extrude'`) can't be told apart by `instanceof` alone, so a `WeakMap<Container, 'stroke' | 'extrude'>` (`containerKind`) tags which shape a given `Container` currently holds. This bit us twice during Pass A/B implementation: forgetting a transition case (Text→Mesh) silently no-ops the new feature instead of erroring, and reusing a `Mesh`'s stale `uvs`/`indices` after only reassigning `.positions` on a topology change (different warp type) silently corrupts the render. Any new per-node-type "sometimes a different Pixi object shape" feature needs its own case in `needsTextRecreate`, not just a renderer-side `update()` change.

**Real 3D extrude** (Phase 3 Pass C):
`extrude3d` effect on a **text** node now renders as real geometry, not `BevelFilter` — `textRenderer.ts` stacks up to 40 flat `Text` clones offset along `(cos(angle), sin(angle))` and progressively darkened (`text/extrudeLayers.ts`'s pure `extrudeSteps`/`extrudeLayerOffset`/`extrudeLayerShade`), the same "stack flat clones" trick multi-layer stroke already uses, just parameterized by `depth`/`angle`/`color` instead of `Stroke.layers`. `applyTransform.ts` strips `extrude3d` from a text node's effects before calling `buildFilters.ts`, so the old `BevelFilter` approximation still applies only to non-text nodes (shapes). This is flat-clone shading, not a true mesh/normal-mapped extrude — upgrade path (real perspective + lighting) belongs to Pass D's custom-GLSL work if ever needed.

**Preset** (Phase 3 Pass D):
A named, canned `{ fill?, effects? }` patch (`src/schema/preset.ts`'s `Preset`, `target: 'text'` always for now) a text node can apply in one click. No dedicated Command — `PresetGallery.tsx`'s apply button dispatches the same `UpdateProps` pattern `FillControls`/`EffectsControls` already use, with the preset's `apply.fill`/`apply.effects` as the patch. `src/presets/builtins.ts` ships 5 curated presets (one per named category: neon/chrome/sticker/retro/3d) rather than the original phase doc's ≥15 — extending the array doesn't change the apply mechanism. **"Save custom preset from current selection" is out of scope** — no name-input UI or persistence layer (document-scoped vs. localStorage) exists for it yet.
_Avoid_: assuming presets are persisted anywhere per-document — applying one is just a normal undoable `UpdateProps`, same as manually editing fill/effects by hand.

**Clipboard**:
Plain in-memory (not OS clipboard) copy/cut/paste/duplicate, scoped to one `<Editor>` mount's lifetime. Composes existing `AddNode`/`RemoveNode` — no dedicated Commands. `deepCloneNode` reassigns a fresh id to a cloned node *and every nested descendant* (grouped clones), not just the top-level id.

**FontService**:
Phase 1 was just a fixed short list of Google Fonts loaded via the `FontFace` API at startup. Phase 3 Pass A adds real upload: `registerFont(family, dataUri)` loads a user-supplied `.ttf`/`.otf`/`.woff2` (as a data URI) via `new FontFace(family, url(...))` + `document.fonts.add()`. Still **not** a glyph-parsing service — no `opentype.js` anywhere in the codebase; every text effect (warp, layered stroke, extrude) works off `PIXI.Text`'s own rendered output, not parsed glyph outlines (see **Warp**).

**Asset**:
A reference (`assetId`) to binary content used by a node, kept out of node props to avoid duplication. `AssetRefSchema` is a discriminated union: `{ type: 'image', dataUri }` or (since Phase 3 Pass A) `{ type: 'font', family, dataUri }`. What an `assetId` *resolves to* is phase-scoped and swappable behind a resolver: Phase 1 resolves it to an embedded base64 data URI stored directly in the document JSON (no backend exists yet); Phase 5's backend resolves the same field to an S3/R2-hosted URL. The document schema field never changes — only the resolution behind it. Note `document.fonts: string[]` is a *separate* list of font family names in use by the document — a `TextNode.font.family` references a family name directly, not an `assetId`.
_Avoid_: File, upload (those are the input side; "Asset" is the referenced, resolved form)

**Image editing** (Phase 4 Pass B):
`ImageNode.crop`/`.mask`/`.filters` all render now via `imageRenderer.ts`, with no new Commands — same `UpdateProps` pattern as everything else (see **Stroke layers**). Three deliberate divergences from the patterns used elsewhere:
- `crop` is normalized 0..1 (fractions of the image's own display box, same convention `TextNode.warp.pathId` points use), not raw texture pixels — `imageRenderer.ts`'s `applyCrop` multiplies by `texture.source.width/height` to get Pixi's native `texture.frame` (no custom crop geometry). Edited via 4 draggable corner handles in `SelectionOverlay.tsx`'s `ImageCropHandles`, entered by double-clicking a selected image node's bounding box (ephemeral, component-local state, not the store — crop-mode is ephemeral UI, not document state).
- `filters` (`brightness`/`contrast`/`saturation`/`blur`) is a flat knob object, **not** the `Effect[]` union `src/schema/effect.ts`/`buildFilters.ts` uses for shapes/text — deliberately different shapes for different purposes, so `imageRenderer.ts` has its own `buildImageFilters()` (`AdjustmentFilter` from `pixi-filters` for brightness/contrast/saturation, `BlurFilter` from `pixi.js` core for blur) rather than extending `buildFilters.ts`.
- `mask: { type: 'shape' | 'text', ref }` points at another node's id. Since a Pixi display object can only have one parent, the ref'd node (which stays a normal visible sibling elsewhere in the page) can't be reused directly as the mask — `imageRenderer.ts` builds a **duplicate** silhouette (reusing `shapeRenderer.ts`'s exported `drawPath` or `textRenderer.ts`'s exported `fillStyle`, not reimplementing geometry), stretched to the image's own `size` bounds (not the ref node's original size/position) — the "drop a photo into a frame shape" convention, not a pixel-accurate overlay clip. Rebuilt from current doc state on every `update()` call, same "just redraw" approach stroke layers use, rather than diffing whether the ref'd node's props changed.

**Asset panel** (Phase 4 Pass C):
`AssetPanel.tsx` lists `document.assets` entries of `type === 'image'` (fonts live in the same dict but aren't node-representable, so excluded) and lets the user add a node that references an **existing** `assetId` instead of re-uploading (which would create a duplicate asset entry). No new Command — same `AddNode` dispatch the Toolbar's file-upload flow already uses; `defaultImageNode`/`loadImageSize` (`Toolbar.tsx`) were exported rather than duplicated. Two entry points, both wired to the same node-creation logic: clicking a thumbnail adds it at the default position; dragging one onto the canvas (plain HTML5 `dataTransfer` drag-and-drop — no library, none existed in the repo before this) adds it at the drop's world position, via `viewport.ts`'s `createViewport(...).toWorld()`, the same screen→world conversion `SelectionOverlay.tsx` uses for click-to-select. The drop target is the canvas column's wrapping `<div>` in `Editor.tsx`, not `CanvasHost.tsx` itself — no changes to `CanvasHost`'s own pointer-handler setup were needed. Extended in Pass E to also list/handle `type === 'svg'` assets (see below).

**SVG import/export** (Phase 4 Pass E):
`SvgNode { type:'svg', assetId, overrides?: Record<string, Fill> }` — `assetId` points at a new `AssetRef` variant (`{ type:'svg', dataUri }`, the raw uploaded SVG markup, same upload path as image/font via `Toolbar.tsx`'s "Add SVG" + `store.addSvgAsset`). Rendering (`svgRenderer.ts`) uses Pixi v8's **own built-in** `new Graphics().svg(svgString)` parser/renderer — the original phase doc named `svgson` as the import parser, but that predates checking Pixi's actual capabilities; **no new npm dependency was needed for rendering**. Per-path recoloring (`overrides: Record<pathId, Fill>`, v1 solid-color only — gradient overrides are schema-valid but silently inert, same convention `buildFilters.ts`'s unknown `custom` shaderId already uses) is done by mutating the SVG source *before* handing it to Pixi, via the browser's native `DOMParser`/`XMLSerializer` (`svgRenderer.ts`'s `applyOverrides`) — also zero new dependencies. `listFillableIds` (same file) enumerates recolorable element ids for `PropertiesPanel.tsx`'s `SvgControls`.
Export (`src/services/svgSerializer.ts` + `exportService.ts`'s `exportSvg`, wired to `EditorHandle.export('svg')`) walks the page and emits real `<rect>`/`<ellipse>`/`<polygon>`/`<line>` vector elements for shapes (including real `<linearGradient>`/`<radialGradient>` `<defs>` for gradient fills — `'texture'` fills fall back to a flat gray, no `<pattern>` mapping yet) and `<image href="...">` directly for `image` nodes. **Text-with-effects is rasterized and embedded as an `<image>`, not outlined to real vector paths** — the explicit decision for this pass, since true glyph-outline vector text needs font-parsing (`opentype.js`), a dependency this codebase has deliberately avoided everywhere else (see **FontService**/**Warp**). `svg`-type nodes are *also* rasterized on export rather than re-embedded as a scaled nested `<svg>` — a ponytail-scoped simplification (imported SVGs stay real vector *on canvas*, just not in a re-exported SVG; revisit if reexportable vector icons become a real need). Both rasterizations reuse the exact same `renderer.extract.base64({ target })` mechanism `exportPng` already used, targeting the live per-node Pixi object via `SceneReconciler.getDisplayObject(nodeId)` — `CanvasHost.tsx` now threads a `reconcilerRef` prop (kept in sync across page-switch/document-reload remounts, since the reconciler instance is recreated then) so `Editor.tsx`'s `export()` can reach it. `ImageNode.crop`/`.mask`/`.filters` (Phase 3 Pass B) have no SVG equivalent mapped yet either — exported images are the uncropped/unfiltered/unmasked source, same "documented v1 cut" pattern as the gradient/texture-fill and svg-node simplifications above.
_Avoid_: assuming SVG import needed `svgson` — it didn't, Pixi already parses/renders SVG natively; only the override/recolor step needed any string manipulation, and that used native `DOMParser`, not a library.
